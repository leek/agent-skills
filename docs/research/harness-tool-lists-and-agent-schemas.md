# Harness model-visible tool lists and Grok/Codex agent-file schemas

Question: What is each harness's full model-visible tool list, and the agent-file frontmatter schema for Grok and Codex?

Started 2026-11-17. Earlier broader survey: `docs/research/agent-harness-capabilities.md` (it found no exhaustive tool table for Codex or Grok and no Grok agent field table).

## Findings

### Grok agent-file schema (answered; source is the binary, docs have no table)
- The bundled user guide (`~/.grok/docs/user-guide/16-subagents.md`, `05-configuration.md`, `09-plugins.md`) never tables the agent frontmatter; it only shows `name`, `description`, `tools`, `mcpInheritance`, `mcpServers`, `hooks`, `permissionMode`, `isolation: worktree`, `disallowedTools`.
- The `AgentDefinition` struct in the installed binary (`~/.grok/downloads/grok-1.0.88-macos-aarch64`, `strings -a`, 2026-11-17) lists these fields, in order: `promptMode`, `toolConfig`, `capabilityMode`, `permissionMode`, `skills`, `discoverSkills`, `inheritSkills`, `injectDefaultTools`, `tools`, `disallowedTools`, `effort`, `isolation`, `background`, `color`, `initialPrompt`, `mcpServers`, `mcpInheritance`, `hooks`, `memory`, `model`, `completionRequirement`, `toolOverrides`, `userMessageTemplate`. `name` and `description` are the identity fields (every bundled agent has them). Evidence the type is the frontmatter: same names appear in docs examples.
- Bundled agents (`~/.grok/bundled/agents/{explore,general-purpose,plan}.md`) use snake_case keys: `name`, `description`, `prompt_mode: full`, `model: inherit`, `permission_mode: default|plan`, `agents_md: true`. So snake_case and camelCase are both accepted (serde aliases), at least for `promptMode` and `permissionMode`; `agents_md` was observed only in snake_case. Prompt body supports template vars like `${{ tools.by_kind.execute }}`, `.list`, `.search`, `.read`.
- Value sets documented: `mcpInheritance` = `all|none|named: [..]|except: [..]`; `isolation: worktree`; `permissionMode` modes `default|acceptEdits|auto|dontAsk|bypassPermissions|plan`; capability modes `read-only|read-write|execute|all`. `tools` accepts a comma string or YAML list, `Agent(type)` restricts spawnable types. Plugin agents: `mcpServers`, `hooks`, `permissionMode: bypassPermissions` ignored/refused.
- Caveat: types and value sets for `toolConfig`, `completionRequirement`, `toolOverrides`, `userMessageTemplate`, `injectDefaultTools` are not documented anywhere found.

Which route a given session uses was not determined.

### Codex agent-file schema (answered from source, tag `rust-v0.169.0`)
- Sources: `codex-rs/agent-roles/src/{agent_role_config,loader,discovery}.rs` and `codex-rs/config/src/config_toml.rs` at `https://raw.githubusercontent.com/openai/codex/rust-v0.169.0/<path>` (the installed version).
- Discovery: for each config layer's folder (`~/.codex`, project `.codex`), every `*.toml` file under `<folder>/agents/` is a role, recursing into subdirectories, sorted by path. Only the `.toml` extension is picked up. Roles can also be declared inline as `[agents.<role>]` in `config.toml` with `description`, `config_file` (path, relative to the declaring `config.toml`), `nickname_candidates`; those `config_file`s are skipped by folder discovery. Duplicate names in one layer warn and the later one is dropped; across layers, a higher layer's fields override and missing fields fall back to the lower layer. A malformed file is ignored with a startup warning, not fatal.
- Agent file = a TOML table with three role-metadata keys plus a flattened `ConfigToml` (the full `config.toml` key set, so any config key such as `model`, `model_reasoning_effort`, `sandbox_mode`, `[features]`, `[skills]`, `[mcp_servers]` parses):
  - `name` (string; required for discovered files, trimmed, non-empty; for a declared `config_file` the table key is the fallback name).
  - `description` (string; required for the role overall, may not be blank; can instead come from `[agents.<role>].description`).
  - `nickname_candidates` (optional array; non-empty, no blanks, no duplicates, ASCII letters/digits/space/hyphen/underscore only).
  - `developer_instructions` (string; required in a discovered file, may not be blank; it is a `ConfigToml` key).
  - everything else = any `config.toml` key. The `RawAgentRoleFileToml` struct has serde `deny_unknown_fields` plus `flatten`, a combination serde does not reliably enforce, so whether a stray key is rejected was not tested. The earlier subagents doc says `sandbox_mode`, `approval_policy`, `model_provider`, `mcp_servers` in an agent file do not override the parent (`https://learn.chatgpt.com/docs/agent-configuration/subagents.md`, cited in `agent-harness-capabilities.md`).
- `[agents]` table (`AgentsToml`, `config_toml.rs` line 763): `enabled`, `max_concurrent_threads_per_session` (alias `max_threads`), `max_depth` (V1 only), `default_subagent_model`, `default_subagent_reasoning_effort`, `interrupt_message`, `job_max_runtime_seconds` (removed no-op), plus the role map. This corrects the earlier note: `max_depth` exists.
- No Markdown/YAML frontmatter exists for Codex agents; Codex skills use `SKILL.md` frontmatter (`name`, `description`), separate from this.

### Codex model-visible tool list (answered for this install; the list is config- and model-dependent)
- Capture method: `codex debug prompt-input "hi"` (codex-cli 0.169.0, 2026-11-17) renders the model-visible input list as JSON; item 0 (`type: additional_tools`) is the tool set. Run from a scratch cwd with the user's normal `~/.codex/config.toml` (model `gpt-6.1-sol`, plugins and MCP servers enabled). Same result with `-c model=gpt-5.6-sol`; `-c features.code_mode=false` did not change it. The switch is the model catalog entry, not a feature flag: `codex debug models` for `gpt-6.1-sol` has `tool_mode: code_mode_only`, `multi_agent_version: v2`, `web_search_provider: standalone`, `supports_search_tool: true`, `experimental_supported_tools: [send_user_message_async, clock]`. `codex features list` therefore misleads here (it shows `code_mode`, `code_mode_only`, `multi_agent_v2` as false while the session uses all three).
- Top-level tools the model sees (namespace `functions` unless noted): `exec` (custom/freeform JS tool, "code mode"), `wait`, `request_user_input`, `request_user_input_async`; namespace `clock`: `sleep`; namespace `collaboration`: `followup_task`, `interrupt_agent`, `list_agents`, `send_message`, `spawn_agent` (params `fork_turns`, `message`, `model`, `reasoning_effort`, `task_name`), `wait_agent`; MCP namespaces, e.g. `mcp__cua_repl`: `js`, `js_reset`.
- Nested tools reachable only through `exec` as `tools.<name>(...)` (documented in the `exec` description, `### ` headings): `apply_patch` (freeform string input), `exec_command` (`cmd`, `justification`, `login`, `max_output_tokens`, `prefix_rule`, `sandbox_permissions`, `workdir`/`yield_time_ms` etc.), `write_stdin`, `view_image`, `list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource`, `request_plugin_install`, `clock__curr_time`. `ALL_TOOLS` inside `exec` lists deferred nested tools omitted from the description. Hosted `web_search` and `update_plan` were not in this item. `prompt-input` shows only the `additional_tools` item (plus messages); whether hosted or request-level tools (for example the standalone web search, `web.run` in `spec_plan.rs`) travel elsewhere in the request was NOT confirmed from source, so this is the tool set delivered in that item, not proven complete.
- Tool names defined in source at tag `rust-v0.169.0` (`codex-rs/core/src/tools/handlers/*_spec.rs`, `hosted_spec.rs`, `spec_plan.rs`), i.e. what other configs can expose: `update_plan`, `shell`, `exec_command`, `write_stdin`, `request_permissions`, `apply_patch`, `view_image`, `get_context_remaining`, `list_available_plugins_to_install`, `request_plugin_install`, `list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource`, `request_user_input`, a tool-search spec (namespace `docs`), the standalone web search `web.run`, `image_gen.imagegen` (names seen in `spec_plan.rs`; `new_context_window` has a spec file but its name string was not extracted), and the multi-agent set `spawn_agent`, `send_input`, `send_message`, `followup_task`, `wait_agent`, `interrupt_agent`, `list_agents`, `resume_agent`, `close_agent` (V1 vs V2 chooses which; this model entry is `multi_agent_version: v2`, hence `followup_task`/`send_message`/`list_agents`). Whether each is gated by a feature was not traced.
- Implication: there is no fixed Codex list. It varies by model catalog entry (`tool_mode`, `multi_agent_version`), `[features]`, plugins and MCP. `codex debug prompt-input` is the best available way to list what a given config delivers, with the caveat above.

## Unverified or open

- Codex list is for one config (code mode on, plugins and MCP on); other configs expose `update_plan`, `web_search`, multi-agent V1 names and so on. Feature gating per tool was not traced. Whether stray keys in a Codex agent TOML are rejected was not tested.
- Grok: which of the two routes (shell vs daemon) a normal interactive session uses was not determined; the live list is from headless `-p`. Agent frontmatter field list comes from binary strings, not a doc or source; value types for `toolConfig`, `completionRequirement`, `toolOverrides`, `userMessageTemplate`, `injectDefaultTools` unknown, and the snake_case/camelCase aliasing was inferred from the bundled agents.
- Claude: headless init omits interactive tools; the docs table is not a strict superset (`DesignSync` is in the build but not the table). The init capture ran with `--safe-mode`, which may drop plugin and mod tools. Interactive session list not captured separately.
- agy: init gives CLI IDs, not the model-facing names (confirmed to differ for read/edit); the mapping is unknown.

## What this unblocks

Answered for all four harnesses from primary sources (live init/prompt-input captures plus docs and source): Claude Code has about 46 documented tools (25 in headless init), Codex shows a small top-level set (`exec`, `wait`, `request_user_input*`, `collaboration.*`, MCP) with `apply_patch`/`exec_command`/`write_stdin`/`view_image` nested inside `exec`, Grok has 27 tools on its shell route, and agy registers 58 CLI tool IDs (model-facing names differ for some). Codex agent files are TOML (`name`, `description`, `nickname_candidates`, `developer_instructions`, plus any `config.toml` key) in `agents/*.toml`; Grok agent files are Markdown with about 25 frontmatter keys read from the binary (plus `agents_md` seen in bundled agents). This makes decidable the per-harness tool-name tables in `skills/harness-tools/SKILL.md` (which pins agy 1.4.12 and Codex 0.166) and which agent-file format each harness needs in this repo's plugin.
