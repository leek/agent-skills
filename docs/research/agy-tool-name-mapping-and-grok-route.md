# agy tool-ID to model-name mapping, and which Grok route an interactive session uses

Questions:
1. What is the agy mapping from CLI tool IDs (the `init.tools` list) to the tool names the model sees?
2. Does a normal interactive Grok session use the shell route or the daemon route?

Researched 2026-11-17 on agy 1.5.10 and grok 1.0.88 (installed locally). Builds on `docs/research/harness-tool-lists-and-agent-schemas.md`, which left both open.

## Findings

### Grok: interactive session route (answered for this install)
- Probe: `grok 'Reply ok. Do not call any tool.'` run in a tmux pty (a real TUI, not `-p`) from an empty scratch cwd, then read the session's own `tool_definitions.json` (`~/.grok/sessions/<cwd-encoded>/<id>/tool_definitions.json`). It lists 26 tools named `run_terminal_command`, `read_file`, `search_replace`, `list_dir`, `grep`, `kill_command_or_subagent`, `todo_write`, `get_command_or_subagent_output`, `spawn_subagent`, `scheduler_*`, `monitor`, `search_tool`, `use_tool`, `workflow`, `enter_plan_mode`, ... `write`. That is the shell-route set; none of the daemon-route names (`Shell`, `Await`, `StrReplace`, `Execute`, `Read`, ...) appear. The new session's `summary.json` has no `session_kind` (headless sessions carry `"session_kind": "headless"`, subagents `subagent*`), consistent with an interactive session.
- Corroboration (consistent with, not proof): among stored sessions in `~/.grok/sessions` whose `summary.json` has no `session_kind` (121 with a tool file), none uses a daemon-route name; across all 262 session tool files, 251 carry `run_terminal_command` and none carries `Shell` (11 have a different tool-file shape and were not classified). Daemon-route sessions may not be stored in that directory at all, so absence there proves little.
- The selector was not found. The docs never state which route is the default or how it is chosen. `~/.grok/docs/user-guide/26-config-reference.md` `features.shared_daemon` ("Daemon route only", "Default false", "A remote rollout turns it on only where none of those is set") governs whether windows share one daemon, not which route runs; `cli.use_leader` and `--leader`/`--no-leader` (`15-agent-mode.md`) likewise. `grok inspect` shows no route field. So the answer is empirical: on this install (grok 1.0.88, `~/.grok/config.toml` has no daemon/leader keys, `experiments_remote.json` has `"experiments": null`) the interactive TUI ran the shell route. Whether a Cursor login or a remote rollout switches an account to the daemon route is unverified; the docs only say Cursor logins show `Account managed` (`02-authentication.md` line 327) and that `XAI_API_KEY` windows keep their own daemon, which implies daemons exist on key logins too.
- `14-headless-mode.md` says "each headless run starts its own daemon" in its workflow-commands passage, yet the headless capture on this install shows shell-route names, so that sentence describes headless runs that are on the daemon route, not this install.

### agy: CLI ID to model-facing name
- Official docs give no mapping. `https://antigravity.google/docs/hooks` uses these as matcher values and `toolCall.name`: `view_file`, `write_to_file`, `replace_file_content`, `multi_replace_file_content`, `list_dir`, `find_by_name`, `grep_search`, `search_web`, `read_url_content`, `run_command`, `manage_task`, `schedule`, `list_permissions`, `ask_permission`, `invoke_subagent`, `define_subagent`, `send_message`, `manage_subagents`, `ask_question`, `generate_image`; it says nothing about model-facing names. `https://antigravity.google/docs/permissions` uses a different vocabulary for CLI permission rules (`read_file`, `write_file`, `read_url`, `execute_url`, `command`, `unsandboxed`, `mcp`); these are actions, not tool names. `https://antigravity.google/docs/sdk/tools` uses a third for the SDK (`list_directory`, `search_directory`, `find_file`, `view_file`, `create_file`, `edit_file`, `run_command`, `ask_question`, `start_subagent`, `generate_image`, `search_web`, `read_url_content`, `finish`, with `BuiltinTools.*` enums). (Docs read through a summarizing fetch.)
- agy binary (`strings -a ~/.local/bin/agy`): protobuf definitions confirm at least two name sets inside the product: tool-config fields `run_command`, `file_edit`, `view_file`, `write_to_file`, `grep_search`, `list_dir`, ... (`antigravity.localharness.*ToolConfig`) and trajectory action types `list_directory`, `find_file`, `search_directory`, `view_file`, `create_file`, `edit_file`, `run_command` (`antigravity.localharness.Action*`), which match the SDK doc table.
- Live stream probe (agy 1.5.10, 2026-11-17, scratch cwd, `agy -p "<list, find, grep, read, create, replace, pwd>" --output-format stream-json --dangerously-skip-permissions`): `step_update` events with `step_type: "tool"` carried `tool_name` values `run_command` (parameter `CommandLine`; the model did the list, find and grep through it, 8 events), `read_file`, `write_file`, `edit_file` (each with parameter `Path`). No `view_file`, `write_to_file`, `replace_file_content`, `list_dir`, `grep_search` or `find_by_name` call occurred, although all are in `init.tools`. The result files confirmed the edit and the create happened.
- Live hook probe (same version, scratch workspace `.agents/hooks.json` with a catch-all `PreToolUse` matcher `""` that logs stdin, a read/create/replace/pwd prompt): the payloads' `toolCall.name` were `read_file`, `write_file`, `edit_file`, `run_command` (steps 2, 3, 5, 7), one for one with the stream's `tool_name`, and `toolCall.args` used `Path`. So in a normal run hook matchers and `toolCall.name` use the model-facing names; the docs' hook examples (`view_file`) did not describe what fired for a file read. The embedded `hooks.md` (`~/.gemini/antigravity-cli/builtin/skills/agy-customizations/docs/hooks.md`) says hook "Tool names are derived by lowercasing the step type and removing the `CORTEX_STEP_TYPE_` prefix", which is the likely origin of the legacy-looking `init.tools` IDs.
- The binary also names the model-facing set directly. Its embedded migration skill (shipped as `~/.gemini/antigravity-cli/builtin/skills/migrate-agent-settings/SKILL.md` lines 157-160) says to write agent-file `tools:` with "the native tool names": `Read`/`Glob`/`Grep` -> `read_file`, `Edit`/`MultiEdit` -> `edit_file`, `Write` -> `write_file`, `Bash` -> `run_command` and `manage_task`, `WebSearch`/`WebFetch` -> `search_web`; a no-`tools` Claude agent becomes `tools: [read_file, edit_file, write_file, run_command, manage_task, search_web]`; an omitted `tools` gets only a small read-only default set. Embedded Go source paths show a `third_party/oneharness/internal/tools/` tree = `ask_question, define_subagent, edit_file, finish, generate_image, invoke_subagent, manage_subagents, manage_task, read_file, run_command, schedule, search_web, send_message, write_file` (+ `provider_tool`, `registry`), alongside a separate `third_party/jetski/cortex/...` tree (its `policyguardian/deterministic_vetting_configs/` has per-tool vetting configs including the legacy `write_to_file`, `replace_file_content`, `multi_replace_file_content`; that directory is not the `init.tools` registry, it only shows the legacy names exist in the product).
- Mapping, best supported (legacy tools take `AbsolutePath` / `TargetFile`, the live ones take `Path`; embedded UI code reads `args.Path || args.AbsolutePath || args.TargetFile` and labels `read_file`/`write_file`/`edit_file` Read/Write/Edit):

| CLI init ID | Model-facing name seen live | Status |
|---|---|---|
| `view_file` | `read_file` | name live-confirmed; equivalence inferred |
| `write_to_file` | `write_file` | name live-confirmed; equivalence inferred |
| `replace_file_content`, `multi_replace_file_content` | `edit_file` | name live-confirmed; equivalence inferred |
| `run_command` | `run_command` | same, live-confirmed |
| `list_dir`, `find_by_name`, `grep_search` | none; the model used `run_command` | no dedicated model-facing tool observed |
| `manage_task`, `schedule`, `search_web`, `ask_question`, `define_subagent`, `invoke_subagent`, `manage_subagents`, `send_message`, `finish`, `generate_image` | same name | in both lists; not individually probed |
| `read_url_content`, `command_status`, `send_command_input`, `wait*`, `browser_*`, `notebook_*`, `call_mcp_tool`, `list_resources`/`read_resource`, ... | unknown | not probed |

- Caveat, both vocabularies appear in shipped material: the built-in `automation` skill (`~/.gemini/antigravity-cli/builtin/skills/automation/SKILL.md` lines 118-121, 227) tells the model to call `write_to_file` and `view_file`, so another model, `--mode`, or the App/IDE may see legacy names. Only the one CLI model (`gemini-4-carbon-medium`, per the hook payload) in default permission-skipping print mode was observed.
- Agent-file `tools:` conflict: `https://antigravity.google/docs/subagents` (summarizing fetch) shows `tools: [view_file, grep_search, run_command]` and warns that an "unmapped or misspelled tool name ... may cause the subagent process to hang". The shipped migration skill writes native names. The hook probe favours native names as the real identity, but no subagent was run to see whether `view_file` is accepted or hangs, so which `tools:` spelling is safe was unresolved here. Resolved later: both spellings are accepted and an unknown name fails fast rather than hanging (`agy-agent-tools-spelling.md`, `agy-mixed-tools-list-and-hang-scope.md`).

## Open / unverified
- agy: no exhaustive model-facing list exists in docs and no model-side tool-declaration capture was obtained, so the table is observation (stream events, hook payloads) plus binary strings, not a spec. `tools:` spelling in agent files unresolved (above).
- Grok: only this install was observed (interactive TUI in a tmux pty, plus stored sessions). The scratch cwd was answered "yes, proceed" at the trust prompt, which adds that scratch folder to Grok's trust list. Login type (Cursor vs xAI key) not checked (credentials not read) and the route selector was not found, so another account or a later remote rollout could differ.

## What this unblocks
- agy: there is no published 1:1 ID-to-name table. In a normal run the model-facing names are `read_file`, `write_file`, `edit_file`, `run_command` (plus `manage_task`, `schedule`, `search_web`, `ask_question`, the subagent tools and `send_message`); `view_file`, `write_to_file`, `replace_file_content`, `list_dir`, `grep_search`, `find_by_name` never fired, and hook matchers saw the native names too, so match `read_file|write_file|edit_file|run_command` in hooks. This settles the agy rows of the tool-name table in `skills/harness-tools/SKILL.md` except the unprobed tools and agent-file `tools:`.
- Grok: a normal interactive session on this install uses the shell route (`run_terminal_command`, `read_file`, `search_replace`, `spawn_subagent`, `workflow`), same as headless `-p`, so skills should target the shell-route names; the daemon-route names (`Shell`, `StrReplace`, `Execute`) are a second case whose trigger is unknown.
