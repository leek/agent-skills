# Implement Spec

Build every ticket of one spec in this session by **orchestrating**, not building: implementer subagents do the code, each in its own worktree; you own the tracker, the **integration branch**, the merges, and the final gates. The goal is the whole spec on one integration branch, every ticket closed, delivered as the user chose: one PR, a stack of PRs (one per ticket), or a pushed branch.

The tickets are not a list of steps. They are a **task graph**: `blocked-by` edges mean there is always a **frontier** of tickets ready to grab, and every ticket on it can be built at once.

Reach for the neighbours instead when they fit better: `/implement <spec> all` builds the same tickets one after another in this session, with no subagents (and is the fallback when the harness has none: say so and stop); `autopilot` builds the same frontier the same way, on the same kind of integration branch, but with a script as the orchestrator and fresh top-level sessions as the implementers, so the run goes on while you are away.

Talk to subagents in **context pointers**: paths to the spec, the ticket, blocker resolutions, notes, commits. Never paste what a pointer already reaches. Ask them for sparse reports. To **follow up** with a subagent (an implementer or fixer), use `SendMessage` to the `agentId` you kept against its label in Claude Code, or the follow-up move in [harness-tools](../harness-tools/SKILL.md) elsewhere; where neither exists, brief a fresh one with its worktree path, its ticket or findings, and the new input.

## Guardrails

- **Never** reset, roll back, drop, or truncate a database this run did not create, or run another destructive data operation on one, without explicit approval. Schema changes go in new migrations.
- Verify identifiers before using them: route names, config keys, enum values, package APIs.

**Stack references.** Identify the stack from its manifests. If a matching file exists below, read it before step 1 and pass its pointer into every implementer brief: it names that stack's destructive commands, worktree setup, test-config files, and formatter.

- Laravel (`laravel/framework` in `composer.json`): [`references/laravel.md`](references/laravel.md)

**Ticket board.** Report each ticket's status per [`ticket-board.md`](../wayfinder/references/ticket-board.md), with `kind: "spec"`: `ready` and `blocked` (note: the blockers) from step 1, `not-built` (note: why) or `skipped` for tickets left out, as that file tells them apart, `running` at dispatch, `fixing` when a failure goes back to its implementer, `merged` (note: the merge SHA, then `verified` once the verifier passes it), `released` (note: why), and `closed` in step 7, or `awaiting-deploy` (note: the after-deploy steps, in a few words) for a delivery ticket left at `ready-for-human`. From step 5 on, also send the `stage` at each change (`review and verify round 1`, `fix pass 1`, `review and verify round 2`, `fix pass 2`, `fix pass 3` when step 5's extra round runs, `final checks`, `deliver`) and each finding's status, so the pane never goes quiet after the last merge. Step 7 sends the `open` list.

## Process

### 1. Load the task graph

Read the spec: its **Build Contract** section first, then what the tickets name. Run `bash <this-skill-dir>/../setup/scripts/ticket.sh frontier <spec slug>` once (`<this-skill-dir>` is this skill's directory; written `ticket.sh` below): its `tickets` give each ticket's `derived` state, `blocked_by`, `claimed_by`, `deploy_gate`, and `delivery`, and its `frontier` the ready ones.

**No `tickets/` yet?** Cut them yourself with `to-tickets`' rules: its step 3 for the slicing, its step 4 for the open decisions, its step 5 and [Ticket template](../to-tickets/SKILL.md#ticket-template) to publish and commit. Vertical slices with honest `blocked-by` edges are what make the frontier wide; a chain of tickets each blocked by the last builds no faster than `/implement all`.

Open the ticket board now, before anything else in this step: load `mcp__leek-skills__ticket_board` with ToolSearch if it is deferred, and send every in-scope ticket with its `title` as `ready` or `blocked`, and each left-out one as `skipped` (closed) or `not-built` (open; note: why).

Leave out closed tickets and tickets claimed by someone else (name them in the report). Never dispatch the delivery ticket (`delivery: true`) to an implementer: you work it in steps 6–7. A `deploy-gate: true` ticket bounds the run: build up to and including it, then stop at step 7 with a PR.

Run `bash <this-skill-dir>/scripts/spec-run-state.sh <slug>` once from the main checkout (read-only, JSON). Its `branch` is the name this run uses wherever this skill says `<slug>`: an earlier run's finished branch moves this one to the next free `<slug>-<n>`. That covers the branch, its worktree, and the notes directory only: the spec's own directory is always `.scratch/<spec slug>/`, never `.scratch/<slug>-<n>/`. When `mode` is `resume`, or a deploy gate has dependents in scope, read [`references/resume-and-gates.md`](references/resume-and-gates.md) now and follow it in steps 1–3.

**Sweep for open decisions first.** Run one read-only subagent over the spec, every in-scope ticket, and the spec's `decisions/` and `research/` (a domain-expert agent type when the harness offers one for the spec's domain). Its brief: list every choice the build will have to make that these documents do not settle, each with the tickets it touches, the line that leaves it open, and a recommended answer. Settled choices (including those `to-tickets`' sweep already wrote to `decisions/`) and pure implementation detail are not open decisions. Most questions a run would otherwise raise mid-build come from here, and asking them now keeps the frontier moving. Skip the sweep when the script's `decision_sweep_done` is true (a committed **Build decisions** ticket from `to-tickets`, and no later commit touched the spec or a ticket): that sweep already covered these documents.

Before the first dispatch (the early one below aside), ask these in one structured-question call ([harness-tools](../harness-tools/SKILL.md); a second call when they pass four; otherwise one message in chat), and nothing else:

- **Open decisions** from the sweep, recommended answer first, in as many further structured-question calls as they need (at most 4 questions each). Step 2 commits the answers to the integration branch; pass that pointer in every implementer and review brief so a reviewer never reopens a settled choice.
- **Worktree**: build the integration branch in a worktree at `.claude/worktrees/<slug>` (recommended: this checkout stays as it is), or switch this checkout to `<slug>`. Skip it when the tree is dirty (the worktree is the only option; say so) or the request already says. Each implementer gets its own worktree either way: that is what lets them build in parallel.
- **Delivery**: `implement`'s [delivery question](../implement/references/delivery-shape.md) for a whole spec: one PR, stacked PRs, or the branch with no PR.
- **Deploy gate**, when dependents wait behind one (per the reference).
- **Resume**, on a resumed run with claims of its own (per the reference).
- **Cleanup**: at the end, remove what step 8 would otherwise ask about (a refused or released ticket's worktree and database, and the verify setup) without asking (recommended), or list them for a choice then. A worktree holding uncommitted work beyond agent notes is always listed, and a branch with unmerged commits always stays.

**Worktree, Delivery and Cleanup are asked once per spec.** When the script's `setup_saved` is true, an earlier run of this spec already asked them: read its `setup` file, say the three choices in one line, and ask none of them. The user changes one by saying so. Otherwise step 2 writes this run's three answers to that file, one per line, for the runs that follow a deploy gate.

**Ready tickets never wait behind the scope question.** When those three choices are known (saved, or given in the request), and some frontier tickets are in every option of the Deploy gate question and touched by no open decision, do step 2 and dispatch those tickets (step 3) before you ask. The answer only adds tickets to the run. Without this, a question asked while the user is away holds every implementer until they return.

Finish when every in-scope ticket and its edges are known, the ticket board lists them (where the tool exists), the open decisions are answered, the worktree, delivery and cleanup choices are made, and the first frontier is listed.

### 2. Create the integration branch

Make a notes directory outside every worktree: the script's `notes` (`<git-common-dir>/implement-spec/<slug>`). Its `screenshots/` folder is the run's one screenshot folder: name it in every brief whose agent may open a browser (the verifier's, each implementer's), so no image sits in a temporary folder that a cleanup removes.

On a resume, set up the integration checkout and `base_sha` per [the reference](references/resume-and-gates.md#resuming-an-earlier-run). Otherwise make `implement`'s [PR delivery: before step 1](../implement/references/spec-run.md#pr-delivery-before-step-1-claims-anything) call: `bash <this-skill-dir>/../implement/scripts/start-branch.sh <spec slug> --branch <slug> --default <default>`, with `--worktree` when step 1's worktree answer (or a dirty tree) says so, `--reset-default` always (it moves local `<default>` back only when that loses nothing), and `--stack --title "<spec title>"` for Stacked PRs. Write its `base_sha` to `$notes/base_sha`, keep `integration_pr`, and do its `todo`. Either way, this checkout is the **integration checkout**.

When step 1 answered open decisions, make that call without `--stack`, then write them in the integration checkout as one closed decision ticket in `.scratch/<slug>/decisions/`, in the format `to-tickets`' Publish step gives its **Build decisions** ticket, and commit it (`docs(scratch): <slug> build decisions`, unless the repo ignores `.scratch`). Only then take `base_sha`: `git rev-parse HEAD`, or for Stacked PRs the `base_sha` that `start-branch.sh <spec slug> --branch <slug> --stack --title "<spec title>" --existing` prints with `integration_pr`. So every ticket worktree carries the answers and no ticket's PR shows them. Answers that arrive after step 1's early dispatch are committed the same way at the integration tip before the next dispatch, and their pointer goes into every later brief; in a stack, the next ticket's PR shows that one file.

Write step 1's worktree, delivery and cleanup answers to the script's `setup` file unless they were read from it.

Read and refresh [Shared exploration](../wayfinder/references/exploration.md) before dispatch, and pass its pointer in every implementer brief. When several tickets still need the same exploration (an unfamiliar module, a package's docs), run one read-only **exploration subagent** first that writes its findings to `$notes` as Markdown (dispatch and wait per [harness-tools](../harness-tools/SKILL.md), otherwise explore inline). Incorporate verified findings into the shared record and commit it before creating ticket worktrees; reuse existing evidence instead of commissioning the same exploration again.

### 3. Dispatch the frontier

Order the frontier by [Build schedule](../to-tickets/references/build-schedule.md)'s remaining critical-path weight, recalculated after each merge. Dispatch up to the concurrency limit (default 5: each one runs a test suite). A ticket waits until a running one merges when a `## Files` path of either appears in the other's `## Files` or `## Shared registrations`; dispatch the next eligible frontier ticket instead. Tickets that overlap only under `## Shared registrations` (append-only routes, translations, provider or config entries) dispatch in parallel and resolve additive conflicts in step 4's merge.

For repeated focused commands, read [Test receipts](references/test-receipts.md) and establish the context before dispatch. Pass its protocol and per-ticket receipt/context paths in implementer briefs; uncertain inputs use fresh execution. Receipts are every brief's default: skip them for the run only for an input that is unknown, with the one-line reason (which input) in `$notes/` and in your dispatch message; a brief never says "fresh" or "no receipts" without it.

1. **Claim** it in the integration checkout: `ticket.sh claim <path> --as implement-spec-<slug>-<run id> --built <NN,NN>` (the tracker's Claim operation), where `--built` lists the tickets this run has merged: they close only in step 7, and without it their dependents are refused as `blocked`. Only you write `.scratch/`; claims stay uncommitted until step 7.
2. **Worktree.** `git worktree add -b <slug>--<NN> <main checkout>/.claude/worktrees/<slug>--<NN> <integration tip>` (the main checkout's `.claude/worktrees/`, never one inside the integration worktree), then make it runnable (install dependencies, copy local env config) the way the project's docs say, or as the stack reference says. When you write the setup into the implementer's brief, point at that recipe rather than restating a shorter one: a hand-written list that skips a step (for Laravel, the `herd.yml` `workspaces.copy` files) fails the implementer's first `artisan` call. When the tests need a real database, give it its own (`<app db>_spec_<slug>_<NN>`, never a name the main checkout's env or test config uses) and register it the moment you create it: `bash <this-skill-dir>/../laravel-herd-worktrees/scripts/scratch-db.sh register <pgsql|mysql> <database> <worktree path>` ([Scratch database registry](../laravel-herd-worktrees/SKILL.md#scratch-database-registry)).
3. **Implementer subagent**, in the background where the harness allows. Where this plugin's agents load, dispatch `leek-skills:implementer` (Claude Code: the Agent tool with `subagent_type=leek-skills:implementer` and `run_in_background: true` where it offers it; elsewhere, that type per [harness-tools](../harness-tools/SKILL.md)). It arrives with `tdd`, `ui-design`, `brand-guidelines`, and `domain-modeling` preloaded. Where the harness has no such agents, dispatch a general subagent in the background per [harness-tools](../harness-tools/SKILL.md). Either way, give it **no `name`** (a named subagent is never woken by its own background command), start its `description` with `<slug>--<NN>` so the ticket board finds it, and write the returned `agentId` into `$notes/<NN>.md` at once, keeping that id against `<slug>--<NN>`. Its brief gives pointers (worktree path, ticket path, the spec's Build Contract, the decisions answered in step 1, direct blockers' reports from step 4, the notes directory) and these rules:
   - Work only in that worktree (enter it with `EnterWorktree({path})` where available, otherwise use absolute paths into it). Confirm `git merge-base --is-ancestor <integration tip> HEAD` before starting.
   - Build test-first. State the seams from `tdd`'s **Seams: where tests go**, then follow its loop until the focused tests and the configured static analysis are green. Before a user-visible change (views, templates, components, stylesheets, or UI-defining classes such as Filament resources, pages, and widgets, or Livewire components), meet `ui-design`'s **Build** done condition. Before user-facing strings (labels, messages, notifications, emails, `lang/` files), follow `brand-guidelines`' **Write** section. Before an ADR or a `GLOSSARY.md` entry, follow `domain-modeling`. When you are `leek-skills:implementer`, those four are already loaded: follow them from the first turn, and read `tdd`'s `references/testing-best-practices.md` and its stack reference (for Laravel, `tdd/references/laravel.md`, a different file from this skill's) before the first test, by the absolute paths written into the brief (`<this-skill-dir>/../tdd/references/…`): a preloaded skill's relative links do not resolve from the implementer's worktree. Any other implementer calls the Skill tool with `tdd` before the first test and with each of the other three before the change that needs it; where the harness has no Skill tool, read that skill's `SKILL.md` by the absolute path written into the brief.
   - Run tests in the foreground and wait for the result. A run too long for the tool's timeout is too broad; run fewer files. Never end your turn while a command you started is still running. If the shell tool moves a command to the background (it does at its timeout), wait for it in the foreground: `bash <this-skill-dir>/../harness-tools/scripts/wait-task-output.sh <the output file it named>`, and run that again while it prints `running`. (Write the script's absolute path into the brief.)
   - Format touched paths with the repo's configured formatter, commit per the `commit` skill's Staging and Subject sections (write `<this-skill-dir>/../commit/SKILL.md`'s absolute path into the brief), leaving `.claude/agent-memory/` out: step 8 carries it. Never touch `.scratch/`, never push, never write another branch.
   - When you look at your work in a browser, save a screenshot as `$notes/screenshots/<NN>-<what>.png` and list its path in the report. Tests that cover the change need no browser.
   - Before reporting, walk the pre-review checklist, the misses reviewers catch most, and fix what it turns up: every writer and reader of each column, status or predicate you changed moves with it, jobs, imports and commands included; each write and the work that must stay in step with it (a sync, a dependent row) commits in one transaction, and locks are taken in one order, never more rows after the caller's own; every rule holds for each party on a shared record, not only the first; and the focused run covers the existing tests of every path you changed, not only the tests you wrote. That run is the repo's own focused-test selection for your changed paths (the command its rules name, or the tests beside each changed file). It runs once here and once after the report-time merge below, and nothing wider: no "risk set" sweep of your own. A large test run costs minutes on every ticket and still misses what CI's full suite catches.
   - Then, once, at report time, merge the current integration tip into the branch and check the focused tests. Never merge it while building: the tip moves under every running ticket, and each merge costs another run. Use the Test receipts protocol for eligible commands, reporting the receipt path and tested tree alongside the result; otherwise run them fresh. Report evidence corrections in run notes for the orchestrator to incorporate.
   - Report in at most ten lines: commit SHAs, touched paths, seams (name any public seam a dependent ticket should reuse), the focused test command and result, deviations from the ticket, each design choice the ticket and spec did not settle with the option it rejected and why, any decision built on an assumed answer, and anything blocking.

Then end the turn and let completion notifications wake you; never poll. An idle notification or completion from an implementer that has not reported is a stall, not progress, even when it says it is waiting on a background run: follow up with it at once, per [harness-tools](../harness-tools/SKILL.md)' stall rule, to finish or say what blocks it. One that repeats a report you already acted on needs nothing: end the turn without a reply.

A hung tool call sends no notification at all. So give every running implementer an idle watch, started with its dispatch: `bash <this-skill-dir>/scripts/worktree-idle.sh <worktree>` as a background shell command (Claude Code: Bash with `run_in_background: true`, never a `Monitor`, which expires after 30 minutes; elsewhere, per [harness-tools](../harness-tools/SKILL.md), or check the worktree's last file change whenever anything wakes you). It exits once that worktree has gone 20 minutes with no file change, or prints `gone` when the worktree is removed. Never hand-write the time check, since `stat` and `date` flags differ between macOS and Linux. Stop an implementer's watch (`TaskStop`) when its report lands, and start a fresh one with each follow-up. Woken by a watch with no new commit, message that implementer to report what it is waiting on, and stop the hung call when it cannot.

### 4. Merge as each implementer lands

With **Stacked PRs**, merge the ticket first and review it afterwards, per `implement`'s [Stacked PRs](../implement/references/spec-run.md#stacked-prs) step 1. Its PR opens at its merge commit, and its review runs while dependents build, so it never holds back the next ticket. Its fixes ship in the closing PR. In the integration checkout: `git merge --no-ff --no-commit <slug>--<NN>`. On a conflict, call the Skill tool with `resolving-merge-conflicts`. Check that ticket's focused tests on the merged tree through [Test receipts](references/test-receipts.md): the check is the focused command the implementer reported, plus the repo's own focused-test selection for any path that command does not cover (a conflict resolution), never a file list you build with `rg` or `find`, which sweeps in the suites the repo keeps out of focused runs (browser, eval, demo). Regenerate context and reuse only matching evidence, otherwise execute fresh: when no merge landed since the implementer's report-time merge, the merged tree is the one its receipt tested, and the helper reuses that run whenever the context matches, per that file. Then commit the merge; on a failure, `git merge --abort`, so `<slug>` only ever holds green merges. With **Stacked PRs**, push and open the ticket's PR right after its merge commit, per `implement`'s [Stacked PRs](../implement/references/spec-run.md#stacked-prs). A failure goes back to the same implementer with the output (follow up with it), so it keeps its worktree and ticket context; a ticket that reports itself blocked is released (`ticket.sh release <path> --note "<why>"`), and its dependents stay out of this run.

Keep each implementer's report in `$notes/<NN>.md`: it feeds dependents' briefs and the ticket's `Resolution`. A merged ticket counts as done for its dependents, so recompute the frontier (`ticket.sh frontier <spec slug> --built <NN,NN>`, every merged ticket listed) and dispatch what it unblocked (step 3).

After each merge, update the ticket board, and post one progress line so the user never has to ask for status: `<NN> merged (<k> of <M>); running: <NNs>; next: <NNs>`, with ` · PR #<n>` after `merged` in a stack. Skip the line when the board's pane shows the run.

**A question never stops the run.** A decision the sweep missed (one that only shows once code exists) is built on its recommended answer when that answer is reversible: the implementer or fixer records it as an assumption in its report, and you ask it at the next merge, so a different answer becomes a follow-up fix, not a wait. When the choice is not reversible (a schema shape a later ticket builds on, a data migration), release that ticket and its dependents, keep building the rest of the frontier, and ask the open questions together at the next merge, or in the final report when nothing else is running. Stop and wait only when every remaining ticket is blocked on an answer.

**Record work outside the spec at once.** When the user decides or asks for something during the run that this spec does not cover (a side grill, a new instrument, a new feature), write it to the tracker in the same turn: a decision record per `grilling`'s [Record the ledger](../grilling/SKILL.md#record-the-ledger), or a ticket. Then send it on the board's `open` list with that path as its `where`, and name it on the end block's **Open** line. Chat holds no copy that the next session can find.

**Verify each ticket as it merges.** One verifier subagent checks every merged ticket while the build goes on, so verification is off the critical path at the end. Dependents never wait for it: they dispatch at merge, as above. After the first merge commit, dispatch it in the background (dispatch per [harness-tools](../harness-tools/SKILL.md); with no background dispatch, verify each ticket yourself after its merge), with **no `name`**, its `description` starting `<slug>--verify`, its `agentId` written to `$notes/verify.md`, and an idle watch on its worktree like an implementer's: started with each handoff, stopped when its report lands, since it sits idle between merges. It does not count against the concurrency limit. Its brief:

- Make a detached worktree, `git worktree add --detach <main checkout>/.claude/worktrees/<slug>--verify <merge SHA>`, runnable by step 3's **Worktree** recipe, with its own registered database (`<app db>_spec_<slug>_verify`) and served the way the verify profile says for a worktree. Never work in the integration checkout: merges change files there.
- Call the Skill tool with `verify` (otherwise follow the `verify` skill, by the absolute path written into the brief). For each ticket handed over, in the order sent: `git checkout --detach <its merge SHA>`, then only the setup that commit needs (dependencies when a lockfile changed, migrations, an asset build when front-end files changed), then check that ticket's acceptance criteria.
- Screenshot every surface checked, pass or fail, as `$notes/screenshots/<NN>-<what>.png`. Write `$notes/verify-<NN>.md`: first line `pass` or `fail`, second line `sha: <the commit checked>`, then each criterion with what was observed, each failure's steps, and the screenshot paths.
- Never edit code, commit, or touch `.scratch/`. Report in at most five lines per ticket: the result, each failure, and the record's path.

Hand it one batch at a time: when its report lands, follow up with every ticket merged since the last handoff, `Tickets <NN> (merged at <SHA>), …: verify their criteria.` A `pass` re-sends the ticket as `merged` with the note `verified`. A `fail` goes back to that ticket's implementer, the same as a failed merge test (`fixing`; its fix merges by this step, and the verifier checks that ticket again at the new merge). When that implementer has finished or cannot be reached, the failure waits for step 5's fix batch. A failure that an external dependency causes is named, never fixed.

Finish when every in-scope ticket but the delivery ticket is merged or released, and no implementer is running. Never wait for the verifier here: step 5's review starts at once, and the verifier's last batch runs beside it.

### 5. Review and verify once, over the whole branch

First dispatch one setup subagent in the background ([harness-tools](../harness-tools/SKILL.md); with no background dispatch, do its work yourself first) that creates the fixer worktrees below, as many as [Parallel fix batch](../triage-github-pr/references/parallel-fixes.md)'s cap of four groups, each made runnable by step 3's **Worktree** recipe with its database registered, so the fix batch dispatches the moment the findings land. Then start both at the integration tip, at once: call the Skill tool with `code-review` against `base_sha` on the integration branch, scoped to every path the run touched and naming its axes (Correctness, Standards, Spec with the spec's path, Design, and UI when the range changes what a user sees; a stack's axes are below), and give step 4's verifier one narrow pass at the tip, as its next handoff once its current batch reports (when none is running, as on a resumed run with no merge, dispatch it now with step 4's brief). That pass covers each merged ticket whose `$notes/verify-<NN>.md` is missing or not `pass`, each ticket whose code changed after the commit its record names (`git diff --stat <sha>..HEAD -- <the ticket's ## Files>`), and each flow the spec's Build Contract names across tickets. It writes the same records and screenshots. A harness with no sub-agents runs that pass inline once the review returns. Verification needs no review fix to start, and its failures join the same fix batch instead of a second cycle. With **Stacked PRs**, every ticket's commits were already reviewed on the Correctness, Spec and UI axes after their merge (their fixes sit on `<slug>` above the top cut), so pass `code-review` the Correctness, Spec, Standards and Design axes (plus UI when a review-fix commit changes what a user sees, aimed at those commits); Standards covers the whole range, since no ticket ran it. Its Correctness brief is aimed at what crosses tickets (shared seams, ordering, one ticket's change breaking another's path) and at each ticket's review-fix commits, which got no re-review of their own. Its fix batch also takes every ticket's BLOCKING and MAJOR `Left open:` findings. Every axis named runs in round 1: the list is the round, not a menu, and an axis left out only moves its findings to round 2.

Fix both sets of findings as one batch, grouped into **fixers** per [Parallel fix batch](../triage-github-pr/references/parallel-fixes.md) steps 1–4 (its merged-tree test run included; the re-review below is its pre-push review, and nothing is pushed): each fixer in a detached worktree `<main checkout>/.claude/worktrees/<slug>--fix-<k>` off the integration tip, labelled `<slug>--fix-<k>` (its database, when it needs one, `<app db>_spec_<slug>_fix<k>`), merged back into the integration checkout. A batch below that file's threshold goes to a single fixer, `<slug>--fix`, working in the integration checkout. Later rounds follow up with each fixer, and a fixer merges the integration tip into its worktree before a later round, so it builds on every earlier fix. Every fixer, the single one included, gets that file's step 2 brief. Mark the findings `fixing` at the handoff, and `fixed` (note: the SHA) for each one whose commit `git log` shows whenever you wake. When you tell the user about findings, name each by what is wrong and where, never by a made-up code (`C2`, `S1`) the user has no key for; once the fixes are merged, re-run `code-review` as a re-review, passing the previous round's findings and head, and follow up with the verifier to re-check only the criteria that failed or whose code the fixes touched. A finding that needs the user's decision never holds the round: send every other finding now, ask that one in parallel, and pass the answer on as a follow-up. Every Design finding (tagged `DESIGN`) is one of these: ask each per [`code-review/references/design-lens.md`](../code-review/references/design-lens.md)'s **Deciding a Design finding** section, and never hand one to a fixer before the user answers **Fix now**. Two rounds is the budget. When the second still has BLOCKING or MAJOR findings, fix those in one more round without asking, its re-review covering only them; name whatever is left in the final report and the PR, with the commit each round reviewed (if the user asks to ship them in a follow-up PR, open **one** follow-up PR for all remaining findings, never one PR per finding, after step 7, based on the integration branch while that PR is open (in a stack, on the closing PR's `<slug>-stack-fixes`, since the remote `<slug>` holds no ticket until triage lands them); once it has merged, retarget per [Follow-up on a delivered PR](../implement/references/spec-run.md#follow-up-on-a-delivered-pr)). Finish when review and verification report nothing actionable, or when the rounds are spent; a verification failure an external dependency blocks is named, and its tickets stay open.

### 6. Final checks

Run [`implement`'s step 6](../implement/SKILL.md#6-run-the-final-automated-checks) once over the whole range. Skip the full-suite question when the repo's rules or the user's saved preferences already settle it (CI runs the suite, or "do not run the full suite unless asked"); otherwise ask once. A declined full suite is never replaced by a broad sweep of many test files: each ticket's focused tests stand as the evidence. A failure the run caused goes to step 5's fixers. Then, when the spec has a delivery ticket, run its pass 1 per [`DELIVERY-TICKET.md`](../to-tickets/DELIVERY-TICKET.md): the full suite and step 5's verify pass count toward its Before merge list, and a coverage gap goes to step 5's fixers like a product failure. Finish when the checks passed and pass 1 is done, or name the exact external blocker and leave those tickets open.

### 7. Close and deliver

For each verified ticket: write its Resolution (what was built, deviations, verification evidence, its implementation commits, seams for successors, from `$notes/<NN>.md`) to a file and run `ticket.sh resolve <path> --body-file <file>`, which appends it, sets `status: closed`, and clears the claim. The delivery ticket closes, or goes to `ready-for-human` with its after-deploy steps copied into the PR body, per its file. Commit the tracker separately (`docs(scratch): <slug> resolutions`), never folded into code. Then follow [PR delivery: after step 8](../implement/references/spec-run.md#pr-delivery-after-step-8) for the chosen shape: push, open the PR (or, for a stack, whose ticket PRs opened as each ticket merged and whose integration PR opened in step 2, open the closing PR and fill in the integration PR's body per its [Stacked PRs](../implement/references/spec-run.md#stacked-prs) step 4), and read review threads once, except on a stack. A fix that is built but not committed or pushed follows that section's **Not yet in this pull request** rule: the delivery is not complete while one exists.

**Screenshots reach the pull requests.** For One PR, open the pull request as ready first (with step 5's `<!-- code-review: head=<reviewed-sha> model=<model> -->` marker) so CI and review bots start before screenshot upload and step 8 cleanup, then attach the uploaded images with `gh pr edit` (keeping the marker intact). Upload the images in `$notes/screenshots` per the `pr` skill's [Screenshots](../pr/SKILL.md#screenshots) section, which inspects each one first, and put them in the pull request's Evidence: in a stack, on each ticket's pull request (its `<NN>-` images) and on the closing one, per [Stacked PRs](../implement/references/spec-run.md#stacked-prs) step 4. After each successful upload, run `bash <this-skill-dir>/scripts/screenshots-report.sh $notes --uploaded <image>...`; an image that section leaves out goes to `--left-out` instead. Then run it with no flag. While its `counts.not_uploaded` is above 0 the delivery is not complete: each such image goes on the board's `open` list as `not-shipped`, with the folder's path as its `where`.

Last, send the board's full `open` list per [`ticket-board.md`](../wayfinder/references/ticket-board.md)'s **Open after this run**, and settle every entry and finding the pane still shows as unfinished per its **Keep the open list true**: entries sent earlier in the run stay on the pane until a call marks them. Work done later in this session (a follow-up fix, after-deploy checks, a triage) updates the board the same way.

### 8. Clean up

Run cleanup from the integration checkout, so `git branch -d` checks each ticket branch against `<slug>`. For each ticket merged into the integration branch, clean up only the environment this run created, in order: carry any change under its `.claude/agent-memory/` into the main checkout's copy (reviewer notes are append-only: add the lines the main copy lacks), then restore the tracked notes (`git checkout -- .claude/agent-memory`, when any are tracked) and delete the untracked ones you carried (`git status --porcelain --untracked-files=all -- .claude/agent-memory` lists them); then run `bash <this-skill-dir>/../laravel-herd-worktrees/scripts/remove-worktree.sh <worktree> --branch <slug>--<NN> --drop-databases` (`laravel-herd-worktrees`' [Remove a served worktree](../laravel-herd-worktrees/SKILL.md#remove-a-served-worktree): clean check, no `--force`, `git branch -d` only). Once git has removed the worktree it drops `<app db>_spec_<slug>_<NN>` and its `_test_<N>` copies, unregisters what it dropped, and names each one it kept, with the reason, in `kept`. A refused removal keeps that ticket's branch, databases, and registry lines together; a refused `git branch -d` keeps the branch (its `-D` hint is not a go-ahead). Name each refusal and each `kept` entry in the report. A fixer worktree `<slug>--fix-<k>` whose commits are merged, or that went unused, goes the same way, with no `--branch`, and so does the verify worktree `<slug>--verify` once delivery is done (stop its idle watch first). List each successful removal. What is left that you created (a refused environment, the environment of an unmerged or released ticket, and any other verify setup: a Herd workspace or database `verify` made for the run outside `<slug>--verify`) follows step 1's cleanup answer: when anything is left, read [`references/leftovers.md`](references/leftovers.md) and do what it says. Keep `$notes/screenshots` while `screenshots-report.sh` counts an image as `not_uploaded`. Keep the integration worktree: it holds the PR branch (leave it with `ExitWorktree({action: "keep"})` if you entered it). Anything kept is `repository-cleanup`'s job later.

## When you're done

Print the end-of-session block using the frame in [`wayfinder/references/pipeline-end-block.md`](../wayfinder/references/pipeline-end-block.md). Its `Pipeline:` and `Done:` lines here are `Pipeline: decide → spec → tickets → **build**   (4 of 4)` and `Done: <tickets closed of total, integration branch, PR, verification state>`. Its **Open** line carries every entry of step 7's `open` list that is not done. Its **Next** conditions:

- **A PR is open and review bots are still running** → `/resolve-review-comments <PR>` once they post
- **A stack of PRs is open** → `/triage-github-pr <every PR, bottom-up>` to land it bottom-up with merge commits
- **Stopped at a deploy gate** → deploy the PR, then `/implement-spec <spec>` for the dependents
- **The delivery ticket is at `ready-for-human`** → merge and deploy, then `/implement <delivery ticket>` for its after-deploy steps; list them
- **Tickets released or left open** → `/implement <ticket>` for each, or `/implement-spec <spec>` again (`/autopilot <spec>` to leave it running)
- **The build exposed a decision nobody made** → `/grill-me` on it, then re-run `/to-spec`
- **The run went sideways** → `/retro this`
