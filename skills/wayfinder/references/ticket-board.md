# Ticket board

A multi-ticket run (`implement-spec`, `autopilot`, `implement <spec> all`, `wayfinder <map> all`) can show each ticket's status in a pane beside the chat. The skill that points here names its statuses; this file holds the rest.

- **Only where it exists.** Use it when the harness lists the `mcp__leek-skills__ticket_board` tool (Claude Code with this plugin; load it with ToolSearch if it is deferred). Elsewhere, skip it: the run is complete without it.
- **What to send.** `board: <slug>`, `kind: "spec"` or `"map"`, and only the tickets that changed, each with `number`, `status`, and a `note` of a few words where the skill names one. The first call lists every in-scope ticket with its `title`; a ticket created mid-run joins with its `title` on its first call.
- **When.** The first call goes out as soon as the run has read every ticket's frontmatter (once they exist, when the run cuts them itself), before any later question, branch, worktree, or claim: the pane is how the person watches the setup too. After that, at every status change, with the changes of one moment in one call.
- **Tickets the run leaves alone.** Send `not-built` for an open ticket this run does not build: held for a person, blocked on something outside the run, claimed by someone else, or the delivery ticket while its blockers are open. Its `note` says why. The pane draws it as open work and the header counts it (`25 of 29 done · 4 not built`), the same as a `released` ticket. Send `skipped` only for a ticket closed elsewhere or ruled out for good: it leaves the count.
- **After the build.** When the skill reaches its review and checks, the pane keeps showing the run: send `stage` (a few words: `review round 1`, `fix pass 1`, `final checks`) at each step change, and `findings` for each actionable review finding, with `id` (any key that stays the same across calls, e.g. `3`; the pane never shows it), `title` (what is wrong, in plain words: `Old workers' runs vanish from the audit list`, never a code like `C2`), and `status`: `open` when the review reports it, `fixing` when it goes to the fixer, `fixed` (note: the fix commit) when that commit lands, `asking` (note: the question) while it waits on the user, and `deferred` when the review budget leaves it open. A call may carry only `stage` or `findings`; `tickets` then stays as it was.
- **Open after this run.** `open` lists the work still open when the run ends. The pane draws it as its own section whenever the list has an entry, and counts it in the header. Each entry has `id` (a key that stays the same across calls; never shown), `title` (plain words), `kind`, `where`, and `done: true` once it is resolved, which strikes it. `kind` is `not-shipped` (built, but not in the pull request), `not-started`, `not-verified`, `your-decision` (waits on the user), or `later` (put off on purpose). `where` is the place it is tracked: a ticket path, a decision record, a pull request, or the literal `untracked`, which the pane marks. `implement-spec` and `implement <spec> all` send the full list in their close step, built from the tracker's open tickets, each review finding the budget left open, each verification that did not happen, work the user added during the run, and every decision that waits on the user. After that, send an entry again whenever it changes.
- **Worker names.** Name each sub-agent that works one ticket `<slug>--<NN>` where the Agent tool takes a `name`; the pane shows its live tool count on that ticket's row. `autopilot`'s workers are separate processes, not sub-agents: their rows show no tool count.
- **The tracker stays the record.** The board never replaces a claim, a resolution, or a status in `.scratch/`.
- **Progress lines.** When the reply says a pane shows the run, skip the skill's chat progress line for that change. When the tool is absent or the reply says no pane shows it, post the line as before.
