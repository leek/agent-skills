# Spec run and PR delivery

Two additions to the `implement` process. A **spec run** builds every ticket of one spec in this session. **PR delivery** puts the work on its own branch, in a worktree when asked, and ends with a pull request. A spec run always uses PR delivery; a single work item uses it when the [delivery question](delivery-shape.md) picks it. `implement-spec` reads the same delivery question and stacked-PR rules.

## PR delivery: before step 1 claims anything

1. Name the branch after the work: the spec's `<slug>`, the ticket's, or a short name for a conversation's scope.
2. Create it from the fresh default branch. One call runs steps 2–6: `bash <this-skill-dir>/scripts/start-branch.sh <slug> --branch <branch>` (`implement`'s directory), plus the flags below. It prints one JSON line, whose `worktree`, `untracked_copy`, `default_reset`, `base_sha`, `integration_pr`, and `todo` these steps use. A failure lists on stderr what it created; nothing is removed.
   - The user asked for a worktree, or the tree is dirty: add `--worktree`. The branch is at `.claude/worktrees/<branch>`, never a sibling directory. Its `todo` is yours: make it runnable (install dependencies, copy local env config) the way the project's docs say, or as the stack reference says, then work there: move the session into it with `EnterWorktree({path: ".claude/worktrees/<branch>"})` where available, otherwise run every command with absolute paths into the worktree.
   - Otherwise it switches this checkout to `<branch>`, and refuses a dirty tree.
3. When the new branch lacks `.scratch/<slug>/` or holds an older copy, the script commits it there (`docs(scratch): <slug>`) from the newest commit that changed it (a deletion or rename counts) where `to-spec` and `to-tickets` commit: local `<default>`, `docs/<slug>-spec`, or the main checkout's current branch (committed, not pushed).
   From here on, the new branch is the only home for `.scratch/<slug>/`. The copies the main checkout keeps block `git pull` on `<default>` after the merge, and they are out of date:
   - **Untracked copy.** `untracked_copy: "deleted"` means it matched the copy just committed. On `"differs"` it stays: name it in the report.
   - **Local `<default>` ahead of `origin/<default>`.** Always add `--reset-default`, without asking. The script moves `<default>` back to `origin/<default>` only when every commit it holds ahead touches only `.scratch/<slug>` and the new branch holds the same `.scratch/<slug>`, so nothing is lost. When `default_reset` is true, say so in the report in one line. When `todo` has a line about `<default>` (other commits are also ahead), say in the report that pulling `<default>` after the merge conflicts on `.scratch/<slug>`, and that `resolving-merge-conflicts` skips those superseded commits.
4. **Stacked PRs only:** add `--stack --title "<spec title>"`. A branch with no commit of its own gets the empty commit `chore(<slug>): open integration branch`, since GitHub opens no PR without a commit.
5. Record `base_sha` from the JSON: the new branch's tip. Claims, resolutions, and code all commit to this branch.
6. **Stacked PRs only:** `--stack` opens the integration branch and its PR now, before any ticket: it pushes `base_sha` to the remote `<branch>` (no upstream) and opens the draft PR `[<slug>] <spec title>`. A draft keeps review bots off a branch that changes with every landing. Keep its number (`integration_pr`): ticket 1's PR is based on it. To run steps 4–6 later (a commit of yours must come before `base_sha`, or a resumed run has no integration PR), leave `--stack` off the first call, then run `start-branch.sh <slug> --branch <branch> --stack --title "<spec title>" --existing`, with `--base-sha <sha>` to push a recorded `base_sha`.

## Spec run

Run it on a spec whose `tickets/` already exist and the user asked to build all of ("`all`", "implement all of …", "the whole spec", or **Every ticket, here** in the scope question). A spec with no tickets yet goes to `to-tickets` first.

1. **Order.** Run `bash <this-skill-dir>/../setup/scripts/ticket.sh frontier <slug>` once: its `tickets` list every ticket in number order, each with `derived`, `claimed_by`, `deploy_gate`, and `delivery`. Take the open tickets in that order (numbers are topological, so blockers come first). A ticket claimed by someone else stays out; name it in the report. The delivery ticket (`delivery: true`) is not built in step 2; it runs in step 4.
2. **Build each ticket inline, one after another.** Per ticket: claim it (step 1, keeping the run's one `base_sha`, and adding `--built <NN,NN>` with the tickets this run already built: they close only in step 8, and without it their dependents are refused as `blocked`), choose its seams (step 2), run the TDD loop with its focused tests (step 3), and commit it (step 4). With **Stacked PRs**, review the ticket, then push and open its PR, per [Stacked PRs](#stacked-prs). Each ticket's commits stand alone, so the PR history reads ticket by ticket. Carry seams a later ticket needs forward in your notes; its `Resolution` is written in step 8.
3. **Stop at a deploy gate.** After a ticket with `deploy-gate: true` is built, run steps 5–8 for the tickets built so far, open the PR, and stop: its dependents start after that PR is deployed.
4. **Run steps 5–7 once, over the whole range.** Review `base_sha..HEAD` scoped to every path the run touched. With **Stacked PRs**, each ticket was already reviewed on all three axes, so this review runs only the Correctness and Spec axes, its Correctness brief aimed at what crosses tickets: shared seams, ordering, and one ticket's change breaking another's path. Ask the full-suite question once. Verify each ticket's acceptance criteria in one `verify` pass. A follow-up fix reruns the focused tests for what it touched, never the full suite again. Then run the delivery ticket's pass 1 ([`DELIVERY-TICKET.md`](../../to-tickets/DELIVERY-TICKET.md)), with no build of its own: the full suite and verify pass above count toward its Before merge list, and a coverage gap is fixed in the run.
5. **Close in step 8.** Resolve each ticket with step 8's `ticket.sh resolve` call; the delivery ticket closes, or goes to `ready-for-human` with its after-deploy steps in the PR body. The spec is complete when every ticket is closed.

**Ticket board.** Report each ticket's status per [`ticket-board.md`](../../wayfinder/references/ticket-board.md), with `kind: "spec"`: `ready` and `blocked` (note: the blockers) at step 1, `skipped` for tickets left out, `running` at its claim, `built` at its commit (note: the SHA), `released` (note: why), and `closed` in step 8, or `awaiting-deploy` (note: the after-deploy steps, in a few words) for a delivery ticket left at `ready-for-human`. From the review step on, also send the `stage` at each change and each finding's status.

## PR delivery: after step 8

1. Push the branch and open the PR with `gh pr create`. Write the body with the `pr` skill's template, its Evidence from the verification pass with the screenshots uploaded as its **Screenshots** section says, then one line per ticket closed, and a `Left open:` line per finding step 5's rounds left open. For **Stacked PRs**, skip this push and PR: the ticket and integration PRs are already open, and the closing PR follows the stack's step 4 below.
2. Read the PR's unresolved review threads once (`bash <this-skill-dir>/../triage-github-pr/scripts/pr-comments.sh <PR> --count`, as `resolve-review-comments` does). When any exist, run `resolve-review-comments` on the PR. When review bots are still running, say so in the end block. For **Stacked PRs**, skip this step: `triage-github-pr` answers the stack's threads, and a push to an open ticket PR would break the rule below.
3. Keep the worktree: it holds the PR branch. If you entered it, leave with `ExitWorktree({action: "keep"})`, which never removes it. Name its path in the report; `repository-cleanup` removes it after the merge.
4. Without a worktree, return the main checkout to the default branch: `git switch <default> && git pull --ff-only`. Say so in the report, so the next request starts on fresh `<default>`.

## Stacked PRs

The build is unchanged: one local branch `<slug>` whose commits read ticket by ticket. Parallel frontier tickets in `implement-spec` still build in parallel; their `--no-ff` merge order on `<slug>` is the stack order, so never ask the user how to linearize parallel tickets for a stack. Each ticket's PR opens as soon as that ticket is **final**, never in a batch at the end, and never before. Final means its code, its review, and its review fixes are all committed. An open PR's branch never gets another commit from the run, so a PR merged early never misses work that lands later.

The stack sits on an **integration branch**: the remote `<slug>`, opened at `base_sha` by [PR delivery](#pr-delivery-before-step-1-claims-anything) step 6, together with its draft **integration PR**. From then on only `triage-github-pr` moves it: stack PRs land into it, then its own fix batches go on it. `<default>` receives the whole spec in one merge, once everything on it is verified. The local `<slug>` holds the whole build and is pushed only as cuts, never to the remote `<slug>`.

1. **Review the ticket first.** Run `code-review` on the ticket's own commits, scoped to its paths, and fix the findings the way step 5 does, in one round: no re-review here, since the whole-branch review (step 4 below) covers every fix commit. In a spec run, do this right after step 4. In `implement-spec`, do it on the ticket's branch `<slug>--<NN>` against the integration tip it last merged, before step 4's merge. The ticket's implementer fixes the findings in its worktree. A finding that round leaves open goes in the ticket's PR body as a `Left open:` line, and its BLOCKING and MAJOR ones join the whole-branch fix batch, so the closing PR fixes them before the stack lands.
2. **Cut and push.** In a spec run, the cut is the ticket's last commit, its review fixes included. In `implement-spec`, it is the ticket's `--no-ff` merge commit on `<slug>`, once the merge passes its focused tests. Run `git branch <slug>-stack-<NN> <cut>`, then `git push -u origin <slug>-stack-<NN>`. The ticket landing `k`th is position `k` (the bottom is 1).
3. **Open its PR.** Base it on the integration branch `<slug>` for position 1 (its `based on` is the integration PR), otherwise on the head branch of position `k-1`. Title it `[<slug>#<k>] <ticket title>`, so the whole stack sorts and reads as one group. Write the body with the `pr` skill's template for this ticket. Its Evidence is the ticket's focused test command and result, and its review outcome. After Merge Danger, add `Stack: <slug>#<k>, based on #<below>. Lands into <slug> bottom-up with merge commits.` Keep each PR number against its ticket: it goes in the progress line and the next PR's `based on`.
4. **Close the stack with two more PRs.** The whole-branch review, the verification pass, and the tracker's resolutions come after every ticket's PR is open. Their commits go on the local `<slug>`, above the top cut, and never onto an open PR's branch. Cut them as `<slug>-stack-fixes` (a name no ticket's cut can take), push it, and open `[<slug>#<n+1>] Review fixes and resolutions`, based on the top ticket's branch. Its body lists each fix with the ticket it touches and the verification evidence per ticket. Then upload each ticket's screenshots from the verification pass (per the `pr` skill's **Screenshots** section, with the ticket's cut branch as `<pr-branch>`), and edit each ticket PR's body (`gh pr edit <n> --body-file <file>`, which adds no commit): add a line saying whether verification passed for it, those screenshots under **After:**, a pointer to any fix in the closing PR, and the whole stack bottom-up (`#101 → #102 → #103 ⇒ #100`). Last, fill in the integration PR's body (`gh pr edit <integration> --body-file <file>`): the `pr` skill's template with the whole run's verification Evidence, reusing those image lines so nothing is uploaded twice, and after Merge Danger the line `Integration: lands <slug>#1 … #<n+1>, then merges into <default>.` It stays a draft.
5. **Report the stack** bottom-up as `#101 → #102 → #103 ⇒ #100`, the integration PR last, with the exact merge order. Name each ticket PR that has a fix waiting in the closing PR. To land it, the next step is `triage-github-pr` on all its PRs, the integration PR included: it lands each PR into `<slug>`, fixes there, and merges `<slug>` into `<default>` last.

A run that stops early leaves its open PRs as they are; the report names them.

A deploy gate ends the stack at the gate ticket, the same as it ends a single PR.

## Follow-up on a delivered PR

A later request that changes the same work ("also fix…", "tweak…") checks the PR first: `gh pr view <branch> --json state -q .state`. In a stack, `<branch>` is `<slug>`, the integration PR: while it is open, the follow-up rides the stack's top and never a lower ticket PR, so no fix has to merge up through the stack. While the run that builds the stack is still going (no closing PR yet), the change joins the local `<slug>` above the top cut and ships in the closing PR.

- `OPEN`: commit to the PR branch, in its worktree when it has one, and push. In a stack, commit to the closing PR's `<slug>-stack-fixes` while it is open, in a worktree at its `origin/<slug>-stack-fixes` (the build worktree holds the local `<slug>`, which is never pushed). Once it has landed into `<slug>`, cut a new branch from `origin/<slug>` and open its PR based on `<slug>`, after Merge Danger the line `Stack: lands into <slug>.`
- `MERGED` or `CLOSED`: the branch is finished. Start from fresh `origin/<default>`: a new branch and PR by default, or straight onto `<default>` when the user says main. An open pull request whose base is that finished branch is retargeted first, onto the new branch or onto `<default>` when the new work goes there: `gh pr edit <n> --base <base>`. Merging it on the old base lands the work on that old branch. Landing a stack still follows `triage-github-pr`'s stacked-PR rules.
